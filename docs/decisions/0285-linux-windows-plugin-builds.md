# 0285: Linux builds and Windows cross-builds of plug-in exports

**Date:** 5 November 2026  
**Status:** Prototype. Linux x86_64 native builds and Windows x64 cross-builds
validated with format validators; no DAW run on either platform.

## Context

The generic CLAP export and the VST3, LV2 and AAX adapters
([decision 0281](0281-generic-export-layer.md)) had been built and validated on
macOS arm64 only. Their documented Windows and Linux commands had not been run.
The project's Windows test machine is a bare Windows 11 virtual machine without
compilers or the Visual C++ Redistributable, and the Linux machine has no
privileged package installation.

## Decision

- **Linux builds natively** with the documented commands. The VST3 adapter no
  longer turns on the SDK's hosting examples: the SDK builds `validator` and
  `sdk_hosting` regardless, and the hosting examples add GTK/gtkmm to Linux
  builds for an editor host that RAVET does not use.
- **Windows builds can be cross-compiled** from Linux (or macOS) with
  `--target windows` on `bundle-clap.py`, `bundle-vst3.py`, `bundle-lv2.py` and
  `bundle-aax.py`. Rust uses `cargo xwin`; the C++ adapters use CMake with
  clang-cl and lld-link through `scripts/cmake/windows-xwin.cmake`, which wraps
  cargo-xwin's own toolchain file and restores the Windows system libraries
  that toolchain clears. The Microsoft CRT and Windows SDK come from cargo-xwin's
  download, never from the repository. Native Windows builds (MSVC, Visual
  Studio generator) stay as documented.
- **Cross-builds link the C runtime statically**: Rust with
  `-C target-feature=+crt-static`, C++ with `/MT` (`SMTG_USE_STATIC_CRT`,
  `RAVET_AAX_STATIC_CRT`, `CMAKE_MSVC_RUNTIME_LIBRARY`). A bare Windows 11
  installation has no `vcruntime140.dll` or `msvcp140.dll`, so `/MD` bundles
  and validators do not load there. Native MSVC builds keep their documented
  defaults.
- **Build-time Windows programs run under Wine** via
  `CMAKE_CROSSCOMPILING_EMULATOR`. LV2 needs this: its Turtle is generated by
  loading the product library, so a Windows bundle's Turtle comes from the
  Windows library rather than from a build-machine copy. The adapters' contract
  tests run under Wine too when it is installed; format validators are
  cross-built and run on Windows.
- Adapter build files make no host assumptions: the VST3 adapter pins the
  MSVC runtime to the SDK's, and lists `CMAKE_CONFIGURATION_TYPES` so
  single-configuration generators place the module inside the bundle; the LV2
  build skips the host's lilv when cross-compiling; the AAX build passes
  rustc's slash-form MSVC options as `-` options so non-Windows CMake does not
  read them as paths. The VST3 SDK's folder-icon step calls Windows' `attrib`;
  cross-builds put a no-op `attrib` on `PATH`, so only the folder's system
  attribute is missing.

## Evidence and limits

Linux x86_64 (Arch Linux): CLAP, VST3 and LV2 Delay bundles pass
clap-validator, the Steinberg validator and the LV2 contract, lilv and
`lv2_validate` checks. Windows 11 x64 (cross-built on that Linux machine): CLAP,
VST3, LV2 and AAX Delay bundles pass clap-validator (built from source with a
static CRT), the Steinberg validator, the LV2 contract tests and the AAX
synthetic-host bundle check, run natively on Windows. Exact counts are in
[work status](../WORK_STATUS.md). No Avid validator, Pro Tools, REAPER or other
DAW has loaded these bundles; editors do not open on Windows or Linux because
the product table hosts Cocoa views only. The LV2 Turtle depends on Wine at
build time for cross-builds; native Windows builds generate it directly.
